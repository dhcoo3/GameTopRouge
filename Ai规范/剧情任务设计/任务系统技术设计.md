# 第一章账号任务与剧情进度系统

> 状态：v1 系统与 M00→M01 配置已落地；Luban 双端生成、剧情/任务配置校验和 Unity C# 编译已通过。MongoDB 账号隔离、重连恢复与完整游戏内流程仍待连服务端实测。当前只录入 M00、M01，其余任务等剧情目标与地图交互点确认后再补。

## 1. 目标与边界

为第一章主线与支线建立可复用的任务框架，并将 C1-M00《失联的巡境骑士》从地图场景临时逻辑迁入正式任务、地图物件和账号进度流程。

- 任务状态、目标进度、剧情布尔标记和道具堆叠按已认证玩家账号保存，不使用房间共享状态。
- 支持多个同时进行的任务，以及调查、对话、击杀、收集目标；支持按阶段顺序推进和“完成其中 N 项”的调查组。
- 使用现有 Luban Excel 配置链、NPC 对话、MapObject 固定物件表、MapData 摆放与地图编辑器。
- 任务完成时服务端自动发放配置中的道具；不做货币、经验、日常/重复任务、放弃任务、完整背包 UI、联机共享任务或服务端战斗模拟。
- 服务端校验当前任务状态、配置来源、目标阶段、请求幂等与奖励唯一性。现有帧同步不提供可靠的位置和战斗事实，因此 v1 不验证玩家距离，也不能证明客户端报告的击杀过程；此限制只适用于当前 PvE 剧情任务。

## 2. 任务规则

### 2.1 状态与解锁

任务状态为 `Locked`（未开放）、`Available`（可接取）、`Active`（进行中）、`Completed`（完成）。新账号没有进度文档时按空进度初始化。

- 任务前置条件由已完成任务和剧情标记组成；同一任务声明的前置条件必须全部满足。
- `AutoOnMapEnter` 任务在进入配置地图时自动接取；`AutoAfterPrerequisites` 任务在前置条件满足后自动接取；`AcceptFromNpc` 任务保持 `Available`，只有配置 NPC 的有效交互才能接取。
- 第一章主线采用自动接取链；支线由配置的委托 NPC 接取。任意时刻可有多个 `Active` 任务。
- 状态只向前变化：`Locked → Available → Active → Completed`；接取后不会因后续剧情标记变化而重新锁定。
- `Completed` 是终态；第一版不存在失败、放弃、重置和重复领取。重新开始章节/清档不属于任务面板操作。

### 2.2 目标组与目标事件

每个任务由按顺序执行的目标组组成。当前组内的目标可并行推进，组的 `RequiredObjectiveCount` 决定需要完成其中几项；该值等于组内目标数表示全部完成。当前组达到要求后才开放下一组。这样可表达 M01“至少调查四处线索中的两处”，也可表达准备阶段的多项必需目标。

目标事件及来源：

| 目标类型 | 服务端检查 | 配置来源 |
| --- | --- | --- |
| 调查物件 | 任务进行中、目标属于当前组、地图与摆放实例一致，且摆放实例绑定同一目标 | `MapData.Objects` 的 `objectiveId` 与 `TaskMarker` 固定物件 |
| 完成对话 | 任务进行中、目标属于当前组、NPC 与对话 ID 符合配置 | 现有 NPC 与 Dialogue 配置 |
| 击败敌人 | 任务进行中、当前目标允许该敌人配置 ID，进度不超过目标数，请求未处理过 | 目标配置的敌人 ID；不验证战斗事实 |
| 收集物品 | 任务进行中、来源摆放实例与物品 ID 符合配置，同一请求/来源不重复计数 | 目标配置的地图物件实例、物品 ID 与每次收集数量 |

目标进度只增不减并封顶于配置值。对话分支由对话图中的 `SetFlag` 节点产生持久剧情标记；如果任务需要统计分支选择，则使用配置的对话选项来源目标。任务条件读取这些账号剧情标记；不存在的标记为 `false`。

### 2.3 剧情标记和简报

剧情标记与任务状态是两个独立字段集合，但同属玩家进度文档。客户端不能直接提交任意标记和值：`DialogueController` 到达 `SetFlag` 节点时提交 `(dialogueId, nodeId)`，服务端只接受 Luban 对话表中确为 `SetFlag` 的节点，并从配置读取标记名和值。服务端确认后客户端才继续执行下一个节点。已提交标记不因对话取消回滚。

任务简报是任务进度的一部分。任务配置可有 `BriefingTextKey`；`QuestProgress.BriefingAcknowledged` 记录确认状态。第一次进入 M00 地图时服务端自动开启 M00，客户端打开简报面板并锁定角色移动；确认请求成功后才解除输入锁。取消或场景退出时保留未确认状态，重新进入时再次显示。简报确认不写入剧情标记。

## 3. Luban 配置

配置均由 Excel 维护，在 `Config/DataTables/Defines` 注册，并通过现有 `Config/gen.sh` 或 `gen.bat` 同时生成客户端和服务端产物。生成代码和二进制文件不得手改。

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `Quest` | `Id`、`Code`、`ChapterId`、`Category`、`SortOrder`、`TitleKey`、`DescriptionKey`、`Activation`、`StartMapId`、`AcceptNpcId`、`PrerequisiteQuestIds`、`RequiredStoryFlags`、`BriefingTextKey` | `Code` 使用如 `C1-M00` 的稳定策划编号；`Id` 为协议和查表使用的整数主键。无用的来源字段为 0。 |
| `QuestObjectiveGroup` | `Id`、`QuestId`、`Order`、`RequiredObjectiveCount` | 按 `Order` 顺序开放；组内达到指定目标数后进入下一组。 |
| `QuestObjective` | `Id`、`GroupId`、`Type`、`DescriptionKey`、`TargetCount`、`SourceMapId`、`SourceInstanceId`、`SourceNpcId`、`DialogueId`、`EnemyId`、`ItemId`、`CollectCount` | 来源字段依目标类型填写。调查或收集目标的地图物件摆放也必须反向绑定本目标 ID。 |
| `QuestReward` | `Id`、`QuestId`、`ItemId`、`Count`、`Order` | 只允许道具奖励；每项数量为正，ItemId 必须存在于现有物品表。 |

`Activation` 枚举为 `AutoOnMapEnter`、`AutoAfterPrerequisites`、`AcceptFromNpc`。目标类型为 `InspectObject`、`CompleteDialogue`、`KillEnemy`、`CollectItem`。任务和目标文案使用 `#Localization.xlsx` 中稳定的 `Quest.` 前缀 key，分别填写简体、繁体和英文译文；道具名称沿用现有物品数据来源。

配置校验在 Luban 生成后执行，失败时阻止交付：

- 任务、目标组、目标、奖励 ID 唯一；组顺序和任务排序无歧义，目标数量为正且组要求在有效范围内。
- 任务前置引用存在且不能形成解锁循环；NPC、地图、对话、敌人、道具和本地化引用存在。
- 对话目标引用有效 NPC/Dialogue；剧情条件标记可由配置中的对话 `SetFlag` 节点产生。
- 调查/收集目标来源必须存在于对应地图固定物件摆放，且 `TaskMarker` 的 `objectiveId` 与目标一致；一个摆放实例只能绑定一个目标。
- 每个主线首组存在合法入口；所有任务目标图均有可达完成路径；奖励可安全计入有符号 32 位堆叠数量。

## 4. 对玩家进度的网络与存档接口

### 4.1 外部接口

新增两个 Gate 请求/响应协议，追加到 OuterMessage，保留现有字段编号；请求中不出现 `PlayerId`。

1. `C2G_LoadPlayerProgress(MapId) -> G2C_LoadPlayerProgress`：从当前认证会话确定账号，读取进度、按配置重算可用任务，并应用当前地图上的自动接取规则后返回权威快照。带地图 ID 的重复调用无副作用。
2. `C2G_SubmitPlayerProgressEvent(RequestId, EventType, QuestId, ObjectiveId, MapId, MapInstanceId, SourceId, Count, DialogueId, DialogueNodeId) -> G2C_SubmitPlayerProgressEvent`：提交接取、目标事件、简报确认或对话标记事件。服务端从会话取账号 ID，校验后原子更新并返回权威快照。

协议枚举事件为 `AcceptQuest`、`ObjectiveProgress`、`AcknowledgeBriefing`、`DialogueSetFlag`。未用字段必须为 0；`RequestId` 为客户端生成的 GUID，整个超时重试过程沿用同一个 ID。去重窗口内，相同 ID 和相同事件内容返回当前权威快照；相同 ID 携带不同内容时拒绝。客户端进度服务同一时刻只提交一个变更，避免对话标记和任务事件乱序；重连后先加载权威快照，再接受新变更。收集数量来自配置，不信任客户端自由输入；普通击杀/调查事件一次只提交一个进度单位。

成功响应带 `Revision` 及完整当前账号进度快照：任务状态和各目标计数、剧情标记、道具堆叠。快照体量按第一章规模控制；客户端只接受不小于当前版本的 Revision。奖励定义和展示文字仍从客户端 Luban 配置读取。

客户端共享服务入口为 `PlayerProgressService.LoadForMapAsync(mapId, token)`、`SubmitEventAsync(event, token)` 和只读 `GetStoryFlag(key)`。任务 MVC 调用服务并呈现快照；对话模块只能经服务提交合法 `DialogueSetFlag` 事件，不直接访问任务 Controller。界面不做乐观完成，只有服务端成功响应才更新目标、解锁、简报状态和物品数量。

### 4.2 服务端校验及错误

所有处理器先用现有 `AuthSceneHelper.TryGetPlayerId(session, out playerId)` 校验当前有效会话；无效会话拒绝。随后检查请求 ID 格式、事件字段组合、表引用、任务状态、目标组顺序和配置来源。重复的已提交请求返回当前快照，不重复加进度或发奖。

响应错误码固定为：`0 Success`、`1 NotAuthenticated`、`2 InvalidRequest`、`3 QuestLocked`、`4 QuestNotActive`、`5 InvalidEventSource`、`6 InvalidObjectiveOrder`、`7 InvalidContentConfig`、`8 RevisionConflict`、`9 StorageUnavailable`。界面通过模块本地化 key 映射错误码；服务端描述只写诊断日志，不用来做业务分支。

事件校验的具体边界：

- `AcceptQuest` 必须是 `Available` 且来源 NPC 与任务表一致。
- 目标事件必须针对 `Active` 任务当前开放的目标组，来源与目标表及 MapData 摆放数据精确匹配，数量不超过剩余目标数。
- `DialogueSetFlag` 必须指向现存 Dialogue 中的 `SetFlag` 节点；客户端不得提交 flag key/value。
- `AcknowledgeBriefing` 必须匹配该活动任务和配置简报；对 M00 还要求 `MapId=1200004`。
- 击杀事实和实际世界距离由当前客户端/帧同步能力决定，服务端不对此作权威判定。此后若加入竞技或经济敏感任务，必须先扩展服务端可验证的玩法事件。

### 4.3 MongoDB 文档与原子性

新增 `player_progress` 集合，每个账号一份文档，`_id` 使用已认证的整数 PlayerId，并建唯一索引。字段语义如下：

```text
_id: PlayerId
schemaVersion: 1
revision: 单调递增的进度版本
updatedAtUtc: 最近一次成功写入时间
quests: { questId: { status, objectiveCounts, briefingAcknowledged } }
storyFlags: { flagKey: bool }
items: { itemId: count }
rewardReceipts: 已发放奖励的 questId 集合
recentRequests: 最近 256 个成功变更的 requestId 与事件指纹
```

首次遇到没有文档的旧账号时创建空进度；不修改现有 `Player`、游客认证文档或本地设置数据。当前 M00 静态内存状态不能迁移，升级后由服务端首次进图重新初始化。

进度、剧情标记、道具堆叠和奖励收据必须在同一 Mongo 文档内一起保存。当前环境不能假定 MongoDB 副本集或多文档事务；实现使用 `revision` 条件替换作为单文档 compare-and-swap：读取、校验并在内存构造新文档，再以旧版本号条件原子替换。冲突后重新读取并重新校验，最多重试 5 次，仍冲突则回 `RevisionConflict`，客户端重载快照后允许再次操作。首写并发以唯一 `_id` 冲突后重读处理。

服务端在同一文档保留最近 256 个成功变更请求的 ID 和事件指纹，用于处理超时重试。客户端收到结果前不提交下一项变更；若连接重建，则先加载快照并丢弃旧连接的待处理请求，再继续提交。接取、简报确认、布尔标记写入和已完成目标本身也都是幂等状态变更。奖励以 questId 写入永久收据；同一 CAS 更新中写任务完成、收据和物品堆叠。道具加法溢出或任何字段校验失败时整份更新不保存。这样避免将进度与奖励分写造成重复发奖。

## 5. 客户端模块和地图接入

### 5.1 MVC 与数据流

- 新建 Quest MVC 模块，按现有 `UIModuleManager`、`ModuleType`、`GameModule` 表注册。Model 缓存服务端快照和选中任务；Controller 编排接取、提交事件、追踪目标和 UI；Panel 呈现列表与详情；View 只提供打开任务面板、简报面板的模块入口。
- 任务面板提供主线、支线、已完成分类；选中项展示简介、状态、目标计数和奖励。单一当前追踪目标 HUD 显示任务名和当前目标；追踪选择只保存在本地 `GF.Setting` 并按 PlayerId 隔离，不上传服务端。
- 简报使用独立可复用 MVC Panel，接收 BriefingTextKey 和任务 ID；服务端确认前保持输入锁。关闭场景或模块时取消等待、解除事件订阅并释放面板。
- Objective 完成描述显示在已完成任务详情中，作为 M00 命令/线索的回看入口；不保存任意对话全文或新增独立存档日志。

### 5.2 地图固定物件

继续使用 `MapObject` 表的 `TaskMarker` 类型和 `MapData.Objects`，不改 NPC 基础表，不由场景脚本动态造任务点。

- `ObjectPlacement` 在原有 10 个字段末尾追加 `objectiveId`。旧记录缺少该尾字段时按 0 读取；编辑器加载、保存、复制、撤销和往返校验都保留此 ID。
- 地图编辑器 Inspector 支持选择/填写任务目标 ID，并验证目标存在、目标地图和任务标记类型匹配。`TaskMarker` 必须绑定有效调查或收集目标；`SceneProp` 的 objectiveId 必须为 0。
- `MapObjectEntity`/`MapObjectMarker` 加载并暴露 placement 的 objectiveId。通用交互层只在该目标属于当前账号的 Active 当前目标组时显示提示；提交时同时发送地图 ID、摆放实例 ID和 objectiveId。服务端再次验证三者与地图表一致。
- 新建可复用巡境记号 Prefab，添加到 `#MapObject.xlsx` 并通过地图编辑器摆到 1200004 村口；不得在 `MapRender` 或场景初始化代码写死坐标。

### 5.3 M00 迁移

1. 首次进入 1200004 时调用 `LoadPlayerProgress(1200004)`；服务端根据 `AutoOnMapEnter` 开启 C1-M00。
2. 若简报未确认，显示“边境哨站记录与队长搜寻令”单页简报，屏蔽移动输入；只有确认 RPC 成功后解除输入。
3. 村口巡境记号由 `MapData.Objects` 中的 TaskMarker 配置，绑定 M00 调查目标。互动只提交目标事件，不直接改 UI 静态状态。
4. 服务器确认调查事件后记录目标完成并完成 M00；自动开启 M01，HUD 目标切换为“向玛拉询问阿尔文的下落”。Mara 的对话门控改为读该目标状态，删除 `C1M00SceneRuntime.IsMaraLocked` 依赖。
5. 移除 `C1M00SceneRuntime` 中的固定坐标标记、静态进度、临时任务 HUD、临时日志和输入锁；移除 `MapRender.AttachChapterOneRuntime`。调查完成说明仍可在任务详情的已完成目标中查看。

## 7. 失败恢复与内容兼容

- 断线、取消或场景销毁停止当前 UI/交互等待并清理订阅。若请求已到服务端且已保存，下一次进度加载会显示提交结果；若未知是否保存，客户端用相同 RequestId 重试。
- RPC 失败时不本地推进任务、不发放本地奖励、不解锁玛拉；保留交互点供重试。只有读档成功后恢复玩家输入和追踪 HUD。
- 服务端配置缺失、版本不匹配或进度文档版本未知时拒绝该操作并记录错误，不按客户端提交的状态兜底。首版客户端与服务端使用同次 Luban 导出和协议发布。
- MapData 旧 `Objects` 字符串 10 字段格式继续可读，ObjectiveId 默认 0；旧 `TaskMarker` 若未绑定目标会被配置校验提示，修复后再启用该点任务行为。
- 任务状态和奖励只按账号存档。进入同一房间的其他玩家加载自己的 `player_progress`，不会收到或修改本玩家任务事件。

## 8. 实施与验收顺序

设计审阅后按此顺序实施：

1. 配置 schema、第一章任务/奖励行、剧情标记引用检查器，生成并验证客户端与服务端 Luban 产物。
