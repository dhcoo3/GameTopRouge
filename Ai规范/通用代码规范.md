# 通用代码规范

本规范适用于客户端和服务器的项目自有代码。客户端与服务器的目录、生命周期和专项要求分别见[客户端代码规范](客户端代码规范.md)与[服务器代码规范](服务器代码规范.md)。项目配置和代码生成流程见[通用项目配置](通用项目配置.md)。

本项目由 Unity 客户端、Fantasy.Net 服务器、Luban 数据表和网络协议工具组成。客户端主要使用 C#，服务器为 .NET 项目。阅读或修改代码时，优先修改项目维护的源代码和配置定义；由工具生成的代码与数据应通过对应流程更新。

## C# 代码质量规范

### 类、成员、方法和参数必须有中文注释

项目维护的 C# 源码中，每个类、结构体、接口、枚举、类成员属性和字段，以及每个方法都必须有中文注释。方法使用 XML 文档注释，每个形参都必须有对应的中文 `<param>` 说明。新增或修改代码时，应补齐涉及类型和成员的注释。构造函数、私有方法、回调、异步方法、接口实现和重写方法也遵循此要求。无参数方法不需要 `<param>`；非 `void` 方法还要说明返回值。属性和字段的注释应说明业务含义、单位、默认值或允许范围；枚举成员应说明其对应状态或用途。

```csharp
/// <summary>
/// 根据玩家列表和关卡配置启动指定玩法。
/// </summary>
/// <param name="players">参与玩法的玩家数据列表，不应为空。</param>
/// <param name="characterId">本次玩法使用的关卡配置 ID。</param>
/// <param name="dungeonType">要启动的玩法类型。</param>
public void Run(List<PlayerData> players, int characterId, DungeonType dungeonType)
{
    // 方法体只编排步骤，复杂逻辑拆分到有明确职责的私有方法。
}
```

注释应解释参数的业务含义、单位、合法范围、是否允许为空及所有权约定；不要只重复参数名或类型。公开成员和跨模块使用的接口尤其要写清楚调用前提、返回结果及副作用。注释与代码行为应保持一致，行为变化时同步更新注释。

自动生成类及其类成员属性、字段也必须带有中文注释。注释应由 `.proto`、Excel、Luban 定义或生成模板等可持续维护的源头生成；不要只在生成文件中手工补注释，以免下次生成时丢失。若当前生成流程没有输出中文注释，应调整源定义或生成模板，并重新生成后检查产物。

### 稳定性

- 在方法入口校验必要的对象、集合、ID 和状态；对外部输入校验范围、序号及重复请求。
- 异步操作明确处理失败、取消和对象销毁后的回调；不要用 `async void` 承载可等待的业务流程，框架事件回调等无法避免的场景应捕获异常并记录必要上下文。
- 订阅事件、注册更新回调或启动计时器时，确保离开流程、销毁对象时可以对应解除或停止；初始化和清理应可预测，避免重复注册与重复释放。
- 访问共享状态和网络回调时明确线程边界；跨线程读写集合时采用一致的同步策略，并缩短锁的持有时间。
- 对网络包、配置数据和集合索引做边界检查；限制缓存、队列和历史记录的增长，并在生命周期结束时清理引用。
- 失败路径应有可定位的日志，不要吞掉异常或只返回默认值掩盖错误。
- 对决定游戏结果的逻辑保持顺序确定，避免使用不同步的随机数、浮点误差敏感计算或无序集合遍历。

### 可读性与短方法体

- 一个方法只负责一个清晰步骤。条件分支和校验过多时，提取语义明确的辅助方法；辅助方法本身仍应避免无意义拆分。
- 主流程方法保持简短，以校验、调用和结果处理为主。复杂算法独立成方法，并用中文注释解释关键规则，而不是逐行翻译代码。
- 禁止新增或生成意义不明的魔数。帧率、超时、容量、状态码等固定值必须定义为有中文说明的常量、枚举或配置项；确实需要直接写数值时，应在附近用中文注释说明其业务含义和单位。
- 使用能表达业务含义的名称，避免含义不明的缩写和布尔参数滥用；复杂条件拆分为命名清晰的变量或方法。
- 控制嵌套层数，优先使用提前返回处理无效输入和异常状态；有资源或订阅生命周期时用明确的清理路径。
- 修改现有结构前先沿调用链确认其生命周期、事件和资源归属，不在 UI、玩法逻辑、渲染、网络层之间复制同一份状态。
